# Внешний авторинг уровней (контракт для LLM вне репозитория)

Документ задаёт минимальный контракт, по которому внешний LLM (без доступа к
репозиторию) может подготовить уровень, переносимый в проект с минимальной
ручной интеграцией. Нормативные правила движка и пайплайна остаются в
[AGENTS.md](../AGENTS.md), [architecture-level-pipeline.md](architecture-level-pipeline.md)
и [architecture-json-levels.md](architecture-json-levels.md); здесь — только то,
что нужно автору контента.

## Что передать внешнему LLM

Передайте одним пакетом (все файлы — в одной папке, чтобы относительные пути
совпали):

1. `level-open.schema.json` — JSON Schema для `kind: "open"` (авторитетная форма,
   экспортирована из `tools/level-schema.mjs`).
2. `external-level-authoring.md` — этот промпт-инструкция (копия из
   `.ai/prompts/external-level-authoring.md`).
3. `castle-authoring/level-castle.json` — рабочий пример сложного средневекового
   замка (стены, ворота, двор, входной донжон, лестницы, ходовая кровля, выход).
4. `castle-authoring/castle-detail.js` — пример опционального детального визуала
   для незаходимых стен/башен.
5. `castle-authoring/APPLY.md` — точные шаги интеграции в репозиторий.

LLM **не** должен угадывать поля движка: источник истины — схема и пример.

## Целевой формат

Использовать **только** `kind: "open"`.

- Это прямые данные карты, которые компилируются в каталог чанков командой
  `node tools/build-level.mjs <file.json>`.
- Не использовать `json`/`json2` (удалены) и не использовать `cityforge` v3/v4
  для ручного авторинга, если задача не про генератор: у open меньше служебного
  boilerplate и он ближе к рантайму.
- `$schema` в брифе: `"./level-open.schema.json"`.

## Единицы и координаты

- Единицы — метры, углы — градусы (`metadata.units: "meters"`).
- Мировые оси: `X` и `Z` — план, `Y` — вверх.
- `ground.y` — отметка плиты земли по умолчанию (обычно `0`).
- `footprint`, `rooms[].polygon` — точки в мировых XZ, обход по контуру.
- Комнаты должны быть внутри footprint здания; порталы дверей — на ребре
  комнаты, наружная дверь — на ребре footprint.
- `rotation` здания/лестницы: только `0/90/180/270` (градусы).

## Семантика данных (что реально влияет на игру)

Данные — источник истины для коллизий, навигации, опоры ног, лучей и картинки по
умолчанию.

| Поле | Эффект |
|---|---|
| `ground` | Квадратная плита мира: `size` — предел карты по XZ. |
| `stream` | Разрезка открытого мира на чанки. `chunk` должен делить `ground.size`. |
| `gameplay.spawn/exit` | Точка A/B. Для `goal:"exit"` выход активируется при достижении `exitRadius`. |
| `roads` | Ходовая поверхность и навигационный коридор. `type:"ground"` — обычная дорога/двор. |
| `buildings[].footprint` | Тело здания: стены генерируются по рёбрам footprint. |
| `buildings[].isEnterable=false`, `rooms:[]` | Закрытый объём без интерьера — годится для сегмента стены/башни. |
| `buildings[].rooms` | Входимые комнаты: пол, перегородки, навигация внутри. |
| `rooms[].connections` | Двери/проёмы. `target` — id дороги/комнаты. `portalPosition` — точка на ребре комнаты. |
| `stairs` | Реальные марши. `straight` требует `dimensions {width,length}` и `rotation`; `ladder` — только `position`. |
| `connectsFloors [k,k+1]` | Связь этажей; `k1 == floorsCount` означает выход на кровлю. |
| `roof.walkable=true` | Ходовая кровля. Нужна для трапа/выхода на крышу. |
| `landscapeObjects` | Визуальный/лёгкий декор (деревья, скамьи и т.п.); не проектировать геймплей на их коллизии. |
| `lights` | Источники света данных. |

### Важные ограничения

- **Ворота/проход в стене** — реальный разрыв геометрии: два сегмента стены с
  промежутком. Не делать «дверь» в незаходимом сплошном здании.
- **Наружная дверь**: комната на первом этаже, `connection.target` = id дороги,
  `portalPosition` на ребре комнаты, совпадающем с ребром footprint; снаружи у
  двери должно быть место на дороге/земле (не внутри другого здания).
- **Лестница**: обе связанные отметки должны существовать (комнаты/этажи ниже и
  выше). Для выхода на крышу нужна `roof.walkable: true`.
- **Углы/стыки стен**: проще и надёжнее отдельные здания-сегменты, не один
  самопересекающийся контур.
- **Детерминизм**: не полагаться на случайность; все id уникальны.

## Детальный визуал (опционально)

Использовать только когда данных недостаточно для силуэта (зубцы, бойницы,
спец. башня). Детальный визуал **заменяет только картинку** незаходимого/обычного
здания, но не коллизию и не навигацию.

- В данных здания: `"detailedVisual": "castle-wall"` (или свой id).
- В коде регистрируется билдер в `src/json-map.js`:
  `DETAILED_VISUAL_BUILDERS['castle-wall'] = (b, bw, bd) => ({ meshes, yOffset })`.
- `bw, bd` — локальные размеры здания с учётом поворота (`detailedLocalDims`).
- Локальные координаты мешей: центр XZ в `(0,0)`, основание в `y=0`.
- Билдер не должен выходить за footprint/габарит коллизии.
- Для `isEnterable` зданий с интерьером generic-картинка стен/полов/крыши
  подавляется, но коллизии/навигация остаются по данным; поэтому кастомный визуал
  keep должен либо отсутствовать, либо полностью воспроизводить читаемость
  интерьера. В примере замка keep использует обычные данные без `detailedVisual`.

## Минимальный набор файлов от внешнего LLM

Обязательные:

1. `level-<name>.json` — бриф `kind:"open"`.
2. `manifest.md` или `manifest.json` — список файлов, зависимостей, сидов/допущений,
   внешних ассетов (если есть) и лицензий.

Опционально (только при необходимости):

3. `<detail>.js` — один или несколько билдеров детального визуала в стиле
   `src/market-row-detail.js`/`castle-detail.js`.
4. `APPLY.md` — точные шаги вставки.

Не передавать сгенерированный каталог `level-<name>/` как источник правки; он
производный.

## Гейты приёмки

Перед передачей автор прогоняет (в репозитории, CI — источник истины):

```bash
# Быстрая локальная подсказка (не гейт):
node tools/build-level.mjs <path>/level-<name>.json --check  # после генерации каталога
node tools/level-parser.test.mjs

# Обязательные гейты в CI:
node tools/check-levels.mjs
node tools/level-parser.test.mjs
# + browser suites через CI workflow / tools/ci-browser.mjs в CI
```

Для примера замка, лежащего вне `src/levels/`, `check-levels` его не увидит;
поэтому в репозиторий добавлен node-тест в `tools/level-parser.test.mjs`,
который валидирует пример, проверяет нулевые предупреждения, связность скелета,
ходовую крышу и детерминизм каталога.

Критерии:

- Ошибок валидации нет.
- Нормализатор не выдаёт предупреждений.
- Скелет открытого мира связный, наружные двери/дороги покрыты.
- Каталог детерминирован (повторная сборка даёт идентичный вывод).
- `exit` достижим из `spawn` по данным навигации.

## Worked example: средневековый замок

Файлы: `.ai/prompts/castle-authoring/level-castle.json`,
`.ai/prompts/castle-authoring/castle-detail.js`.

### Состав

- **Куртина**: 4 незаходимых здания `cw_*`, `floorsCount:1`, `floorHeight:8`,
  `rooms:[]`, `detailedVisual:"castle-wall"`. Южная стена разорвана на западный и
  восточный сегменты — промежуток `x=-12..12, z=36..40` это ворота.
- **Башни**: 4 угловые + 2 привратные, незаходимые, `floorsCount:3`,
  `detailedVisual:"castle-tower"`.
- **Двор**: `road rd_court`, `type:"ground"`, от `z=44` (снаружи ворот) до
  `z=4.3` (перед дверью донжона).
- **Донжон**: один enterable `keep`, footprint 20×16, 3 этажа по 4 м,
  `roof.walkable:true, parapet:0.9`.
- **Комнаты**: `hall` (floor 0), `great_hall` (1), `solar` (2), каждая на весь
  footprint. `hall` имеет наружную дверь `main_entrance` в `rd_court` в точке
  `(0,0,4)` на южном ребре.
- **Маршрут**: `spawn (0,44)` → ворота/двор → дверь `(0,4)` → `st_hall_to_great`
  → `st_great_to_solar` → `st_solar_to_roof` (ladder, connectsFloors [2,3]) →
  `exit (0,-4)` на кровле, `y=12`.
- **Декор**: 4 дерева, 2 факела-точки у ворот. Фонари дороги выключены, чтобы не
  попадать в тела привратных башен.

### Почему так

- Стены — данные, значит твёрдые и блокируют навигацию без отдельной физики.
- Ворота — отсутствие геометрии, значит проход гарантированно есть.
- Keep — обычный building с комнатами/лестницами: движок уже умеет полы, проёмы,
  лестницы, крышу и навигацию.
- Кастомный визуал только на стенах/башнях: не ломает interior-картинку keep.

## Шаги интеграции в репозиторий

См. `.ai/prompts/castle-authoring/APPLY.md`. Коротко:

1. Скопировать `level-castle.json` в `src/levels/`.
2. Сгенерировать каталог: `node tools/build-level.mjs src/levels/level-castle.json`.
3. Зарегистрировать главу в `src/levels/index.js` (импорт + LEVELS + LEVEL_NUMBERS).
4. Скопировать `castle-detail.js` в `src/` и зарегистрировать билдеры в
   `src/json-map.js` (импорт + записи в `DETAILED_VISUAL_BUILDERS`).
5. Прогнать гейты CI. Не коммитить временные артефакты.

## Ограничения текущего контракта

- Контракт проверен для `kind:"open"`, осевых/простых полигонов, обычных зданий,
  дорог, лестниц, ходовых крыш, декора и детальных визуалов.
- Сложные наклонные геометрии, кастомные физические тела, скриптовые триггеры и
  runtime-логика вне данных — не часть этого контракта.
- Если нужен новый тип данных/движкового поведения, сначала расширить схему и
  движок, затем обновить этот документ и пример.
